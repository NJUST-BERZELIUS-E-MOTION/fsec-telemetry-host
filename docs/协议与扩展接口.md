# 数据协议与扩展接口说明

> 配套固件: `单片机代码/Lora/Lora测试板`
> 关键文件: `HARDWARE/LoRa/Telemetry.c`、`SYSTEM/log/log.c`、`USER/main.c`

## 1. 串口参数

| 参数 | 值 |
| --- | --- |
| 串口 | USART1(PA9/PA10) |
| 波特率 | 115200(`uart_init(115200)`) |
| 数据位 / 校验 / 停止位 | 8 / 无 / 1 |

## 2. 固件输出内容

接收板(测试板)每收到一个 LoRa 数据包, 中断回调 `OnDataReceived()`
(Telemetry.c) 经 USART printf 输出**单对象一行 JSON**, 以 `\r\n` 结束。
按首字节 `config_id` 分三类:

```json
{"rssi":-65,"type":"burst","config_id":10,"frames":[{"ts":1234,"hv_voltage":312.00,"hv_current":1.11,"accel_ratio":...,"slip_ratio":...,"vehicle_speed":...,"target_torque":...,"slip_limit":...}, {"ts":...}, ...]}
{"rssi":-65,"type":"event","config_id":20,"ts":5678,"vehicle_status":1,"vehicle_flags":0,"wss_online":0,"battery_online":1,...,"acc_brk_timer":0}
{"rssi":-65,"type":"data","config_id":1,"ts":9012,"hv_voltage":312.00,"hv_current":1.11,...}
```

| 包 | config_id | 内容要点 | 上位机处理 |
| --- | --- | --- | --- |
| burst 周期合包 | 10 | 1 包合 N 帧(默认 4), 每帧 `ts + 7 通道`(hv_voltage/hv_current/accel_ratio/slip_ratio/vehicle_speed/target_torque/slip_limit) | 拆成 N 条样本逐帧显示/保存 |
| event 事件流 | 20 | 状态变化即发; `vehicle_flags` 位域展开成 8 个布尔键(wss_online/battery_online/inverter_online/sc_closed/acc_brk_conflict/pedal_unreliable/ready_btn/hv_btn) | 一条样本 |
| data 单帧 | 1/2 等 | 按 `Rx_Config_Table` 通道表解析, 字段随配置变化; 含 vehicle_flags 时同样展开; 未注册 config 输出 hex 兜底 `"payload"` | 一条样本 |

> 传感器全集、量纲与分组见 `config/fields.json`(键 `key` 与固件 `Sensor_Table` 的
> `JSON_Name` 一一对应); 上位机对未在表中的新键自动注册并归入"动态字段"。

同一条串口还会出现 `Log_Write()` 的文本日志(以 `\n` 结尾), 例如:

```
SPI Check Success
temp = a5
RX DONE
seq=3,ack_ctrl=65
Ack True, RTT=12 ms
```

**结论**: 串口是"日志 + JSON"混流, 上位机必须按行切分、逐行试解析
(解析失败按日志处理); JSON 行再经拆帧解码为样本
(见 `TelemetryRecord`), 这是本工程三层拆分的直接原因。

## 3. 上位机流水线

```
QSerialPort (115200, 8N1)
   │  readyRead 字节流
   ▼
SerialReceiver        采集层: 累积字节 + 按 '\n' 切行(兼容 '\r\n'),
                     半包留缓冲, 一次事件可切出多行
   │  lineReceived(QByteArray)
   ▼
JsonFrameParser       解析层: 盖 PC 时间戳/帧序号,
                     逐行 QJsonDocument::fromJson
   │  frameReady(Frame)   Frame{ seq,time,kind(Log|Json),raw,json }
   ▼
SinkManager           分发层: 同一帧广播给所有已注册 ISink
   ▼
RawLogSink         TelemetrySink        (未来: FileSink/ChartSink/StatsSink...)
原始数据窗口        遥测表格+计数         仅需实现 ISink 并注册
```
说明: TelemetrySink 收到 JSON 行后先经 `decodeTelemetryFrames`(TelemetryRecord)
拆帧(burst 逐帧/event/data → 0..N 条样本), 再逐条交给界面与 FileSink;
界面按样本自适应字段, 记录文件为结构化样本 JSONL(一行=一条样本)。

所有环节都在 GUI 线程内同步执行, 不跨线程, 逻辑简单清晰;
将来若串口频率高到影响界面, 只需把 `SerialReceiver + JsonFrameParser`
移到一个工作线程对象(信号槽自动排队), 界面侧无需改动。

## 4. 扩展新数据处理方式(ISink)

接口(`src/core/ISink.h`)只需实现两件东西:

```cpp
class ISink {
public:
    virtual ~ISink() = default;
    virtual QString name() const = 0;                  // 处理器名
    virtual void onFrame(const Frame &frame) = 0;      // 每条帧都会到这里
    virtual void onReset() {}                          // 串口重开时复位
    virtual void setPaused(bool paused) {}             // 暂停/恢复呈现
};
```

以"保存 JSON 到文件"为例 —— **该示例已落地实现**:
`src/sinks/FileSink.{h,cpp}` + 主界面记录栏("保存到…"选目录/命名, "开始记录/停止记录"),
接入方式即下面的三步模式(见 `MainWindow` 构造与 `sinks/FileSink.*`):

```cpp
// 1) 新类 src/sinks/FileSink.h —— 骨架
class FileSink : public QObject, public ISink {
    Q_OBJECT
public:
    // ... name()/onReset()/setPaused()
    void onFrame(const Frame &frame) override {
        if (!m_file.isOpen()) return;
        if (!frame.isJson()) return;          // 只记 JSON, 保持 JSONL 纯净
        m_file.write(frame.raw); m_file.write("\n");  // 原始文本一行一条
        m_file.flush();
    }
private:
    QFile m_file; // 由 start(path) 打开(目录自动创建, 已有文件则追加)
};

// 2) MainWindow 构造处注册(约两行)
m_fileSink = new FileSink(...);
m_sinks->registerSink(m_fileSink);
```

> 注意: FileSink 刻意不响应 `setPaused()`(继承基类空实现), 因此界面"暂停刷新"
> 不会打断正在进行的文件记录——记录只由"开始记录/停止记录"控制。

同样模式可做: 遥测曲线(QtCharts 已随 Qt 6.11.1 安装)、字段统计、
UDP/共享内存转发、超阈值告警、回放模拟源(从文件喂帧)等。

界面呈现与流水线解耦的原则: 出口只发信号, `MainWindow` 负责把信号画到控件上
(见 `RawLogSink → appendRawLine()` 的连线方式)。

## 6. 与固件联调自检清单

1. 打开串口后, 原始数据页应出现固件启动/运行日志(如 `SPI Check Success`);
2. 另一块板定时发 LoRa 遥测, 接收板打印 JSON → 原始数据页出现绿色 JSON 行;
3. 遥测数据页最新值随帧刷新, 速率/帧数持续累加;
4. 拔掉 USB 再插回, 程序提示端口异常并回到"未连接", 可重新打开 —— 属正常行为。
